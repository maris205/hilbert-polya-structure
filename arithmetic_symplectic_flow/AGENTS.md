Research workspace for Round-2 **candidate engineering**: a proposed
arithmetic suspension flow over one concrete symplectic map. This directory is
new; the existence of the directory is not a mathematical candidate, Route
result, or authorization to run research.

## The controlling invariant: one object

Before discussing A0, A1, A2, a determinant, a trace, or an operator, verify
that all of these belong to the **same frozen candidate**:

```text
phase space (M, omega)
specific symplectic base map F and parameters
positive roof tau
mapping torus / suspension flow phi^t
arithmetic mechanism and permitted data
primitive closed-orbit and repetition convention
symbolic coding, if any
transfer operator, zeta/determinant, domain, and normalization
controls
optional later Hamiltonian/contact/quantum owner
```

Never construct a narrative from a symbolic clock, a distinct physical flow,
a borrowed determinant, and another operator. If an object, roof, normalization,
or owner changes, stop the current candidate or create a new candidate ID and
fresh P0 card. Do not transfer theorem statements, source locks, Route credits,
or authorizations from Logistic, Hénon, Symplectic, Symbolic, or Flow work.

The term *symplectic* applies first to the base map. A mapping torus of a
\(2n\)-dimensional base is \(2n+1\)-dimensional and is not automatically a
symplectic manifold or Hamiltonian flow. Any Hamiltonian/contact/quantum lift
requires its own exact construction and owner relation.

## Research integrity and reporting

- Freeze a versioned candidate card before a theorem claim, computation, or
  Route language. Unknown information is `OPEN`, not implicitly inherited.
- Do not manually insert \(T_p=\log p\), von Mangoldt weights, prime tables,
  Riemann-zero data, or per-prime parameter choices as the claimed endogenous
  arithmetic mechanism.
- Record positive controls, negative controls, ownership controls, cutoff /
  precision limits, and `PROVES_TOO_MUCH` risks where applicable.
- Keep source identity, workflow state, local mathematical result, numerical
  observation, heuristic, and Route status distinct. A clean build, a paper,
  or a completed checklist is not a proof or gate closure.
- Preserve negative, stopped, `OPEN`, `NOT_TESTABLE`, and inconclusive results.
  Do not overwrite an old candidate to make a new idea look continuous.

## Paper and file standard

All substantive work belongs in a Markdown paper package under `papers/`.
Follow [papers/README.md](papers/README.md) and
[papers/paper-template.md](papers/paper-template.md): `paper.md` is the full
record; `candidate-card.md` and `claim-ledger.md` carry the identity and scope.
Update root [readme.md](readme.md) only with a concise linked overview after
the detailed paper record is current.

This Round-2 workspace is Markdown-only. Do not create or regenerate LaTeX,
PDF, or publication artifacts unless a current user request explicitly changes
that scope. Do not modify linked Phase-I source materials merely to make a new
paper easier to read.

## Verification and handoff

Use checks proportionate to the actual change. At minimum, verify Markdown
links and that the paper, candidate card, claim ledger, and README name the
same candidate ID and status. For a mathematical or computational result,
record exact inputs, commands/methods, output locations, limits, and controls;
do not infer infinite/global claims from finite checks.

Before handoff, say clearly:

1. which candidate and object were studied;
2. what is established, negative, heuristic, open, or not testable;
3. whether the same-object ledger remained intact;
4. which Route coordinates were actually evaluated, if any; and
5. the next authorized decision or stop/fork condition.

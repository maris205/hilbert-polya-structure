# Five-paper research workflow

This is the prospective C-series operating workflow. Existing frozen batches
retain their own contracts. Paths below are relative to the repository root.

## 1. Recover and scope

Read the current state, active batch contract, and Git status. Identify the
latest user authorization, completed work, exact pending gates, and any live
processes. Preserve unrelated files. A summary is a pointer, not proof that a
process exists or a check passed. Update state at meaningful milestones.

Use only the history needed for the current mathematical dependency or source
collision. Do not reopen all earlier papers or reread every installed skill.
Once a skill is selected, read its full entry instructions and required
references; choose additional skills only when their capabilities apply.

## 2. Select substantial contracts

For each candidate, state the object, parameter family, clock, domain,
observable/determinant convention, arithmetic mechanism, and intended theorem.
Separate classical inputs from the proposed increment. Search the repository
for the same object, conjugate mechanisms, and previous obstructions; verify
relevant primary literature and record what was actually accessed.

Prefer intrinsic arithmetic structure with a plausible A1/A2 bridge. A source
classification or no-go result qualifies when it closes an important complete
question, not merely because an exact computation or known formula is available.
Define a cheap decisive feasibility check before a large census or paper draft.
If the claim collapses to a known result, a parameter table, or an already
excluded model, replace the subtype. Preserve the rejection and its reason.
Subtype changes stay within this authorized C-series research batch; they do
not authorize advancing another stream's batch or entering Route B.

Freeze one batch plan with five independent contracts and completion criteria.
Candidate scouting and reserve systems are not completed papers. Do not assign
success labels or invent a theorem to fill a vacant slot. If five defensible
contracts cannot be found, report the concrete limit instead of manufacturing
five outputs. A proven scoped obstruction is a result, not an automatic A2 pass.

## 3. Prove and build in parallel

Give each author disjoint package paths and one complete contract. Reserve
global state, shared infrastructure, and Git integration for the coordinator.
Send only the source definitions, needed references, boundaries, and expected
handoff; avoid copying the entire repository history into every subtask.

Proofs must cover quantified parameters, limiting operations, domains,
multiplicities, signs, and exceptional cases relevant to the claim. Mark
external theorem dependencies and distinguish exact, certified, numerical,
conditional, conjectural, and refuted statements.

Use executable evidence where it tests something substantive. An independent
checker must reconstruct the claimed result by an independently justified path;
rehashing a producer's output is only an integrity check. Symbolic identities,
high-precision checks, adversarial controls, and finite censuses are selected
for the actual theorem and evaluator requirements, not to reach a test quota.
Do not fabricate experiments when a proof-only argument is appropriate.

## 4. Evaluate and review

Apply the pinned evaluator without relaxing its scientific gates. Record
unperformed or inapplicable checks with reasons; a missing control is not PASS.
Formal evaluations follow its required reference routing. A narrow question
about an explicit failure condition may be answered directly without writing
a full evaluation or updating registries.
Preserve the full route tuple and scope flags. A source-system determinant or
counting law alone does not promote a target-arithmetic grade.

Obtain at least one substantive independent internal review of each new paper's
proof, closest-source ownership, and evidence. Supply the reviewer with the
theorem and primary artifacts; ask for counterexamples and precise gaps, not
an approval score. The coordinator adjudicates findings. Repair blocking issues
and have their affected reasoning checked again. Additional full reviews are
justified by unresolved risk or an explicit batch requirement, not a fixed loop.

If an applicable external skill or frozen contract requires more review,
preserve that requirement or resolve its conflict explicitly; do not silently
declare a shortened process equivalent. External upload/review still needs
its own authorization. Current-team review is never described as human review.
When a selected skill names an unavailable tool or older reviewer default,
identify that requirement and use its allowed fallback with the current team
for prospective work under the user's Astra instruction. Do not pretend the
named external review ran. If a frozen contract specifically requires that
external review, report that gate as unresolved; continue other authorized work.

## 5. Write and release each paper

Provide readable LaTeX and an actual PDF containing a complete argument or
precise links to a complete proof supplement. Credit classical results and
state limitations. Save genuine review-driven revisions when made; no minimum
page count, mandatory section count, or artificial three-version history.

A complete package contains the theorem/claim boundary, primary-source notes,
proof, manuscript and PDF, applicable code/results/checks, evaluation, review
record, and reproducibility/release record. Related narrative material may
share a file when that improves clarity. Do not create boilerplate solely to
match an old directory's file count.

For a new release, run all package-required checks on final inputs. Rebuild the
final PDF in two fresh build directories under recorded deterministic settings;
compare bytes, inspect fonts/text/warnings, and visually inspect every final
page. Changes to the proof, numerical method, or release code need their
affected checks; a prose-only index edit does not need every mathematical lane.

Use an exact payload ledger plus a self-excluding manifest. Include all actual
payload files; reject unexpected members and symlinks where the release contract
forbids them. For release code changes, test actual failure paths before writes,
including a tampered payload whose digest was recomputed. Do not generalize one
test count into universal security. Run the final read-only verification after
sealing. A hash match establishes byte identity, not mathematical correctness.

Record the commands, inputs, environment, exit statuses, and relevant hashes.
Reuse a receipt only when its relevant inputs and environment are unchanged.
After required gates pass, stop testing unless a change, failure, or concrete
unresolved concern invalidates a result. Avoid several agents rerunning the same
heavy lane solely to repeat PASS; their effort should test different failure modes.

## 6. Integrate and hand off

Update the current state, batch result, and relevant registries once the
substantive result changes. Stage exactly the authorized packages and related
indexes. Inspect any remote advancement for overlap before integration; do not
overwrite another stream, force-push, or include unrelated untracked files.

Report five actual PDF links, the independent increment and route judgment of
each paper, unresolved limits, completed verification, and real synchronization
status. Stop at the five-paper checkpoint. Publish elsewhere only under separate
user authorization. Do not let a successful build stand in for a research result.

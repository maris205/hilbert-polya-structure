## Canonical format and finite retention

The prospective stdout format is p212-ascii-canonical-json-v1: sorted own
enumerable object keys, original dense array order, null/boolean/safe integer
numbers (reject -0), and strings preserving every UTF-16 code unit.
Every code unit outside printable ASCII, and quote/backslash, is written
as lower-case backslash-u plus four hexadecimal digits. This includes each
surrogate unit; splitting the 16,384-unit chunks cannot replace or normalize
a Unicode value. Other printable ASCII, including every hex digit, is copied.
Exactly one final LF follows the complete JSON value. No getter/toJSON hook,
function, cyclic/nonplain object, unsupported numeric value or sparse array
is evaluated as data.

The writer has a 256 MiB / 268,435,456-byte stdout cap, 8 MiB entry-diagnostic
cap, 8,192 value-node bound and depth 32. One input-string chunk becomes at
most 98,304 encoded bytes. Each successful positive write return advances
the exact offset/count; zero/error/unsupported structure/bound failure is
failure, never success with a clipped suffix. FD 1's identity projection
and size are checked against actual reported writes, and a returned successful
FD 1 close is necessary for native zero. FD 2 stays available for a stdout
close failure and settles at ordinary actual native completion; no explicit
stderr-close, continuous snapshot or post-final-runtime attestation is claimed.

The eight-file reader retains at most 102,760,449 candidate bytes including
its one possible failing overflow sentinel, hence at most 205,520,898 hex
characters. These source-level bounds are not actual observations. The
256 MiB envelope cap leaves room above this candidate-hex bound and the small
bounded request/control structure; arbitrary unusual exception data can
still hit the fail-closed cap. The original reader still holds its own
buffers/hex strings in memory. Streaming the serializer adds no hard memory,
wall-time, storage reservation, filesystem-return or guaranteed-liveness claim.
The entry's diagnostic cap does not globally bound native bootstrap/runtime
stderr writes, which go to the separate raw file.

Normal reader partial/failure returns are serialized completely and produce
native 78, not acceptance. A request/entry exception or unreturned reader
produces native 79 and, when safe and no output progress is reported, a
failure envelope retaining the actual request-input and returned-value state.
Otherwise only best-effort diagnostic data is added to stderr while existing
partial stdout is preserved. Primary and secondary error descriptions are
kept when a failure-envelope write also fails. A fatal allocation/IO/process
failure can make the original internal reader rows or later transport
unavailable; reader_called=true/reader_returned=false does NOT prove no
candidate observation occurred. No missing internal value, byte suffix,
exception object or native return is reconstructed. No bytes/files are
overwritten, deleted, retried as observations, or reclassified as complete.

Native zero is only a candidate for later original-data reception. Require
the actual complete native request and every return/continuation, empty
separate native control output, the complete closed stdout file, empty raw
stderr, valid complete canonical value and every actual reader/input record.
Hash/count/preview/record status is not acceptance. Bootstrap/import/setup
failure can precede the entry; the raw redirections preserve diagnostics

# Research workflow

This is the execution guide for `flow_systems`. The [proposal](../propose-flow-systems.md) supplies scientific aims; the current request supplies the authorized work. This guide does not itself start a batch or clear a stop condition.

## Select the task

| Request | Use |
| --- | --- |
| Explain, diagnose, or review | Inspect the relevant materials and report evidence; do not implement an unrequested fix. |
| Change code or instructions | Implement the scoped change and run appropriate local checks. |
| Continue a named research stage | Resolve that stage's current inputs, authority, completed work, and outstanding obligations below. |
| Assess Route A or Route B | Use the corresponding `.agents/skills/flow-route-*/SKILL.md`; an assessment is not permission to run new experiments. |
| Start a new research batch | Apply the batch policy below, within the user's chosen scope and resources. |

## Continue an existing stage

Start from the latest relevant user instruction and its referenced checkpoint. Read the exact approval/request, input lock, and completion or STOP receipt that determine the next action. Follow explicit successor links; filenames, modification times, README summaries, and the largest round number do not establish authority or completion.

Keep one concise working summary of the objective, writable targets, protected inputs, completed checks, unresolved findings, and next action. Reuse valid completed work when its inputs and contract still apply. Do not create another approval package or replay the whole history merely to restate an unchanged decision. Create formal records when the selected protocol actually requires them.

An explicit validation/hash/build stop is a real boundary. Preserve the failure and state the smallest action needing authorization. A later instruction to continue does not by itself authorize changing locked evidence or weakening a gate. For ordinary incidental failures outside such a stop contract, use safe, scoped recovery and disclose remaining limitations.

## Perform the authorized work

Use the installed academic-research workflow when the task calls for it; select only the relevant workflow, role, and required references. Discover its current installed location instead of copying a plugin version path from an old script. This repository guide does not replace its scientific or evidence requirements.

Parallelize independent papers, source checks, or bounded implementation tasks. Identify shared inputs and assign a single writer to each output. The main agent reconciles findings and verifies that a claimed result is supported by the returned artifacts, not only by a worker's summary.

Keep the candidate's object, arithmetic origin, clock, normalization, determinant convention, data split, and evidence level explicit. Do not fit definitions to target prime/zero tables, combine incompatible constructions, or promote numerical observations into theorems. Record ideas outside the continuous-flow family as `ROUND2_CLUE` without launching a new family.

For an authorized manuscript revision, preserve its continuous revision chain and use the applicable patch/authority protocol. Notes-side drafts and preview PDFs remain separate from canonical `paper/` artifacts until promotion is authorized. Literature metadata establishes identity; a claim needs relevant passage support and an accurately stated scope.

Before executing an existing helper, check its actual input versions, write destinations, overwrite behavior, and import-time effects. There is no general-purpose current runner in `tools/`: a historical builder may write canonical PDFs or receipts even when its name sounds diagnostic. Reuse reliable mechanics where applicable; do not reuse old verdict maps or fabricate execution times.

## Verify and hand off

Select the smallest sufficient checks plus all checks explicitly required by the active protocol. For instruction changes, check metadata, links, routing, or realistic decision behavior only where affected; a spelling fix does not require a full skill evaluation. For a code change, check the affected behavior. Scientific claims and stage completion require their prescribed evidence and coverage; prompt-efficiency advice does not lower those requirements.

Report what actually changed, what was checked, the result, and any remaining limitation. Distinguish incomplete work from a failed final audit. Preserve failed attempts and append new evidence when correction is authorized. Update progress indexes, canonical outputs, or remote repositories only when those actions are included in the current scope.

## New-batch policy

When the user authorizes a new research batch, continue existing paper numbering and complete at most five meaningful paper projects before the batch review. Choose the next question from the preceding result: reproduce an anomaly, strengthen a positive result, investigate an obstruction, or test the smallest justified alternative. Do not create papers merely to meet the count, and do not launch a sixth without the next batch authorization.

Use the proposal's project layout and author information. Produce paper-first deliverables at the authorized stage, maintain the requested local progress index, and evaluate Route claims before promoting them. Synchronize to the established session destination only when Git/sync is authorized and available; preserve unrelated work. A transient sync failure alone need not halt otherwise authorized local research.

Stop the batch early for an exhausted scientific scope, a genuine dependency requiring user input, or a major result requiring independent reproduction and adversarial review. Active stage-specific checkpoints and stop conditions still apply. End with the completed projects, strongest supported result and obstruction, reusable structure, remaining obligations, and recommended next direction.

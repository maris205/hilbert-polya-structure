The outer source opens no repository, source-file, image-file, mountinfo,
pathname-inventory, or cleanup object. It owns both exact direct children.
Every direct-child wait transition stores raw status and removes live
ownership in one `physical_reap` assignment before any deadline check,
drain, parse, or other fallible work. Primary failure is write-once; cleanup
failures are separate and can only demote PASS.

## 5. Exact group-keeper source

The group keeper is the outer's second direct child. The outer places it in
the still-live launcher's new process group before releasing the launcher.
It self-binds its source, environment, flags, image and topology, blocks all
catchable signals, writes one exact readiness record, and then waits on an
outer-held pipe. It creates no child, changes no limit, opens no repository
object, and has no delivered-signal call. The outer never writes the hold
pipe. Therefore an armed keeper can leave only through the outer's bound
group SIGKILL or an out-of-premise external event; loss is FAIL.

## 6. Exact owned-launcher source

The launcher is the outer controller's one direct child, process-group
leader in the unchanged outer session, and deadline-owned helper. It performs every potentially blocking identity,
procfs, source-file, mount, inventory, and cleanup operation. A synchronous
call is bracketed by internal checks, but that is not claimed to bound the
syscall. Containment comes from the still-live outer controller, which can
terminate the whole owned group if the launcher does not return by the total
deadline. The launcher accepts a successful call only after its post-call
deadline check.

The launcher receives the exact keeper PID only through the outer arm record.
It checks the record's field count, order, terminal LF, EOF, canonical
decimals, direct-parent relation, its own leader PGID, the keeper's live PGID,
and the common outer session before opening any governed object or setting a
hard CPU limit. It then preserves V4's held-image, held-ledger, held-control,
component-safe directory, mount exclusion, identity-stable rmdir, exact
marker file actions, telemetry, parsing, cleanup, and terminal rechecks.

A returned helper call is accepted only after its post-call check. Internal
checks do not claim to interrupt a blocking call; the still-live outer and
group keeper supply that containment. If launcher control fails after marker
spawn, the launcher emits its exact cleanup request and quarantines. If a
default-fatal signal or hard RLIMIT_CPU kills it instead, no quarantine
premise is needed: the keeper still binds the group and the outer still owns
the cleanup authority.

## 7. Exact unified-marker source

The marker remains the sole owner and reaper of its normally completing
nested children. It emits returned PID immediately after spawn, every raw
stdout chunk with sequence/count/hash/lowercase hex, and raw wait status
immediately after the one physical-reap state transition. The launcher
forwards those bytes while retaining an identical copy. Missing status is
never synthesized.
